## 1. 阶段 P0：必须先修

### F1　错误信息脱敏不得吞掉原因
- 现状：`thinking_core._sanitize_error` 取 `splitlines()[0]`；Google 的错误体是多行缩进 JSON，第一行是 `{`，用户只会看到 `HTTP 400: {`。
- 要求：
  1. `call_llm_json` 读到 HTTPError 响应体后，先尝试 `json.loads`，取 `error.message`（Gemini）或 `error.message`/`message`（OpenAI 兼容）；解析失败则把空白压缩为单个空格后取前 160 字。
  2. 然后再做 Key 脱敏（替换 `api_key` 原文与 `key=...` 模式）。
  3. `_sanitize_error` 改为：压缩空白、脱敏、截断 160 字，不再取首行。
- 验收（单元测试）：构造含换行的 Google 风格错误体 `{\n "error": {"code": 400, "message": "API key not valid"}}`，断言返回文本含 `API key not valid`；构造包含该请求 Key 原文的错误体，断言结果不含 Key。

### F2　转发层异常与总时限
- 现状：根 `server.py` 的 `_proxy_sub_agent` 用 `timeout=120`，无 try/except；子 Agent 单次调用最多 3 次尝试、每次 60 秒，generate 还可能再来一次修复重试。超时或 `_get_sub_agent_port` 导入失败时异常直接抛出，连接被掐断，`do_POST` 中退额度的代码不会执行。
- 要求：
  1. **转发层**：`_proxy_sub_agent` 全程包在 try/except 内：`socket.timeout`/`TimeoutError` → 返回 504，其余异常（含 `_get_sub_agent_port` 导入失败、连接被拒）→ 返回 502；均为 JSON `{"error": "...", "category": "服务异常"}`，文案不含内部异常细节（托管模式）。函数**始终返回状态码**，使 `do_POST` 的 `status >= 400` 退额度逻辑生效。
  2. **总时限**：`thinking_core` 增加请求级总预算 `LLM_TOTAL_BUDGET`（默认 100 秒，环境变量可改，必须小于转发层 120 秒）。generate/extract 入口记录起点；`call_llm_json` 每次尝试的超时取 `min(cfg.timeout, 剩余时间)`，剩余不足 5 秒则不再重试；`run_generate` 的修复重试仅在剩余时间 ≥ 35 秒时进行，否则直接按校验失败处理。
  3. 无法保证"一定不超过 120 秒"时，以 100 秒为目标即可，汇报中说明实测方式。
- 验收（单元测试，不联网）：
  - 把转发超时临时改小（如 1 秒），子 Agent 打桩为睡眠 3 秒，经根服务请求，断言返回 504 且 `quota` 计数已退回（用临时库，断言前后 reserve 计数）。
  - 让 `_get_sub_agent_port` 抛异常，断言返回 502 且已退额度。
  - 对 `call_llm_json` 打桩使其每次耗时 40 秒（用假时钟，不要真睡），断言总预算耗尽后不再重试。

### F3　`/api/route` 不得无计量使用服务端 Key（D9）
- 现状：根 `server.py` 的 `_handle_route` 在托管模式且无用户 Key 时仍用服务端 Key 调模型，只受每 IP 每分钟 120 次的限流约束。
- 要求：托管模式下，仅当请求体带用户自己的 `api_key`（判定方式与子 Agent 转发层一致：非空、非 `server-configured`、不含 `...`）才调用模型；否则只返回规则路由结果，`engine` 仍为 `rule`。非托管模式行为不变。
- 验收（单元测试）：托管模式下无 Key 请求，断言 `thinking_core.call_llm_json` 未被调用；带 Key 请求，断言被调用。

## 2. 阶段 P1：质量退化与设计缺口

### F4　恢复 B1 丢失的 prompt 约束（最重要的一项）
- 现状（已对照 `docs/archive/council_backup_20261127/agent5_server.py` 确认）：新生成的 prompt 丢失了——标题 ≤16 字、摘要 ≤35 字、每条 detail 35~60 字、共识/分歧 35~55 字、各 section 内**每条目**的具体 tag 与 name 提示（如"主要矛盾/暂缓处理/暂缓处理"）、"冷静、务实、直击本质，不要喊口号"的语气要求、抽取 `summary_note` "35字以内提示最值得补充的 1~2 项"。其余 6 个 Agent 很可能有同类丢失，**需逐个核对**。
- 配置格式扩展（向后兼容，缺省则不输出对应约束）：
  ```json
  {
    "style_note": "原 prompt 中的语气/风格要求，原样",
    "title_hint": "16字以内",
    "summary_hint": "35字以内",
    "extract_summary_hint": "一句话提示用户最值得补充哪 1~2 项信息（35字以内）",
    "sections": [
      {
        "heading": "...",
        "items": [
          {"tag": "主要矛盾", "name_hint": "矛盾名称（12字内）", "detail_hint": "为什么它决定全局……（35~60字）"}
        ]
      }
    ],
    "synthesis_hint": "共识/分歧各 35~55 字"
  }
  ```
  `sections[].items` 存在时，prompt 按条目逐条列出（条数即 items 长度）；不存在时沿用现有 `count`/`item_tag` 写法。
- 要求：
  1. 对 agent4–agent10，**逐个**打开备份 `docs/archive/council_backup_20261127/agentN_server.py`，把其 `_generate_ai` 与 `_extract_ai` prompt 中的上述约束原样搬入各自 `config.json`；`build_generate_prompt`、`build_extract_prompt` 读取新字段。

- 验收（单元测试）：对每个 Agent，从备份文件中用正则提取旧 prompt 里的长度约束字样（如 `35~60字`、`16字以内`），断言它们全部出现在新生成的 prompt 中，或在对照表里被标记为"按新契约替代"。不得再用"标题字符串出现在 prompt 里"这种恒真断言。

### F5　截断改为宽松上限
- 现状：`_trunc` 在 60/30/40 字处硬切，中文输出常超限，界面会出现残句。
- 要求：将字数限制视为"目标"，硬上限取目标的 1.5 倍（向上取整）。超过硬上限时，在硬上限内最后一个标点（，。；、！？）处截断并加"…"；找不到标点则在硬上限处截断并加"…"。未超过硬上限则原样保留。对 `verdict`、`would_change_if`、`action`、`decision`、`assumptions` 生效。
- 验收（单元测试）：80 字的 verdict 在 90 字硬上限内原样保留；120 字的 verdict 在标点处截断并以"…"结尾。

### F6　校验 pillars、sections 等结构
- 现状：`validate_result` 只校验 `council_notes`。xAI/DeepSeek 无 schema 约束时，`sections` 不是数组会让前端 `.forEach` 抛异常。
- 要求：在 `validate_result` 中新增校验，错误并入同一个 `errors` 列表（因此会触发同一次修复重试）：
  - `title`、`summary` 为非空字符串。
  - `pillars` 为长度恰好 3 的数组，每项 `value`（或 `content`）非空。
  - `sections` 为数组，长度等于配置的 sections 数；每个 section 的 `items` 为非空数组，每个 item 含非空 `name`、`detail`。
  - 通过后，服务端用配置中的 `heading` 回填各 section 的 `heading`（不信任模型），用配置中的 `label` 回填 pillars 的 `label`。
- 验收（单元测试）：`sections` 为字符串、`pillars` 只有 2 条、`items` 缺 `detail`，各自产生错误；一次修复重试后合法则通过。
