## 1. 任务

### G1　补全 F4（最重要）

**现状**：对照备份，agent7、agent10 的旧 prompt 有一段"核心要求"：
- "紧扣用户的具体案例，拒绝空泛鸡汤与教科书式套话，直指要害"
- 落地动作清单的领域指引：agent7 为"先做客观事实核验，再做心理误判隔离，最后给出冷静决策与边界"；agent10 为"如果是泡沫给出撤离/隔离步骤，如果是真复利给出借势/复用步骤"

新配置里 `style_note` 为空，这些全部丢失。agent4、6、8、9 **未被核对**，大概率有同类丢失。

**要求**：
1. 配置新增可选字段 `extra_rules`（字符串数组）；`build_generate_prompt` 在"语气与风格要求"之后输出"补充要求："并逐条列出。分节的专属指引用 `sections[i].guidance`（字符串，可选），渲染在该节的行末。
2. 对 agent4–agent10，**逐个**打开备份 `agentN_server.py`，提取 `_generate_ai` 和 `_extract_ai` 两个 prompt 中的每一条规则/约束（包括"核心要求"下的每一行、长度限制、语气要求、抽取规则），逐条处理：
   - 能原样搬入的：搬入 `style_note` / `extra_rules` / `guidance` / 各 `*_hint`，措辞不改。
   - 只有以下几类允许不搬，并必须在汇报里写明：① 旧 council 的 25 字限制与写死的 `stance`（被 B2 新契约替代）；② "请结合上下文合理推演"（B3 有意舍弃）；③ "4 位智囊各自独立发声"（D2 措辞决定）；④ 旧 `steps` 键（JSON 结构里不存在，其内容应改写为对应 section 的 `guidance`，如上）；⑤ 旧 pillars/sections 的 JSON 模板示例（由配置生成）。
   - 其余一律必须搬入。
3. 按 D10 处理 `count`。
4. 汇报给出**逐 Agent、逐条**对照表：旧约束原文 → 新位置（字段名）或"允许不搬+类别"。不得只写"已搬入"。

**验收**：见 G2。

### G2　把 F4 测试改成真正能发现丢失

- 现状：`test_f4` 只检查几个字数字样，且直接读取 `docs/archive/` 的备份，归档一旦被清理测试就挂。
- 要求：
  1. 新增 `tests/fixtures/council_constraints.json`：由 G1 的逐条提取结果生成，每个 Agent 一个列表，元素为 `{"text": 旧约束原文, "where": "generate"|"extract", "status": "required"|"dropped", "reason": "仅 dropped 需要，写 G1 中的类别"}`。
  2. `test_f4` 改为读取该夹具：对每个 `required` 条目，断言 `text` 作为子串出现在对应的新 prompt 中（`build_generate_prompt` / `build_extract_prompt`）；`dropped` 条目必须有 `reason`。
  3. 加一个负向测试：把某个 Agent 配置里的 `style_note` 临时置空，断言 `test_f4` 的检查函数能报出缺失（用函数形式实现检查，便于负向调用）。
  4. 夹具不依赖 `docs/archive/` 存在；另外保留一个**可选**的 `tools/extract_backup_constraints.py` 用于重新生成夹具（读取备份，仅在人工运行时使用）。

### G3　强制并回填条目结构

- 现状：`validate_result` 对 sections 只要求 `items` 非空，且把模型给的 `items` 原样透传（含多余字段、非字符串类型）；prompt 里 agent5 的"每节固定 3 条、各有固定 tag"不被校验。
- 要求：
  1. 若配置的 section 含 `items`（逐条目配置）：模型返回的条数必须**恰好等于**配置条数，否则作为校验错误并入同一次修复重试；通过后，服务端用配置中同序号条目的 `tag` **回填**。
  2. 若配置的 section 不含 `items`（仅有 `count`/`item_tag`）：不强制条数；超过 8 条时静默截断到 8 条；`tag` 取模型给的非空值，否则用配置的 `item_tag`。
  3. 重建每个条目为 `{"name": str, "tag": str, "detail": str}`，三个键均强制转成去首尾空白的字符串，丢弃其他键。
  4. `pillars` 同样只保留 `label`、`value` 两个键（`label` 已由配置回填）。
- 验收（单元测试）：agent5 返回 2 条而非 3 条 → 报错且触发修复；返回 3 条但 tag 乱写 → 通过且 tag 被配置值覆盖；条目含 `{"x": 1}` 多余键或 `name` 为字典 → 多余键被丢弃，非字符串被转成字符串或判错（`name`/`detail` 为字典、列表一律判错）。

### G4　标题、摘要、支柱、条目详情的长度上限

- 现状：除智囊判断外，其余文本无上限；模型写超长会原样入库、原样展示。
- 要求：新增 `parse_max_len(hint)`：从提示文字里解析字数上限——匹配 `(\d+)\s*[~～-]\s*(\d+)\s*字` 取第二个数，或 `(\d+)\s*字以内` 取该数；解析不到返回 `None`。对 `title`（取 `title_hint`）、`summary`（`summary_hint`）、每个 pillar 的 `value`（取对应 `hint`）、每个条目的 `detail`/`name`（取对应 `detail_hint`/`name_hint`），解析到上限则用现有 `_trunc(…, 上限, 字段名)` 处理（1.5 倍硬上限、标点处截断加"…"）；解析不到则不处理。
- 验收（单元测试）：对 `parse_max_len` 覆盖 `"16字以内"`、`"35~60字"`、`"报告标题，18字以内"`、`"45~90字深度拆解"`、`""`；120 字的 title（上限 18、硬上限 27）被截断并以"…"结尾。

### G5　Gemini schema 被拒时的降级（D11）与本地检查

- 现状：`responseSchema` 从未对真实 Gemini 验证过；若被拒，每次 generate 都会 5xx。
- 要求：
  1. `call_llm_json` 的 HTTPError 分支：当 provider 为 gemini、`e.code == 400`、本次请求带 `responseSchema`、且提取出的错误信息（小写）含 `schema` 时：从 `payload["generationConfig"]` 删除 `responseSchema`，重新生成 `data`，打印 WARN（不含内容），在**同一轮重试序列中**继续（消耗一次尝试）；该降级只做一次。
  2. 新增 `tools/check_schema.py`：对 agent4–agent10 调用 `build_generate_schema`，本地检查所有节点只使用 Gemini 支持的键（允许集合：`type`、`properties`、`items`、`required`、`enum`、`description`、`nullable`、`format`），`type` 为大写枚举，`enum` 只出现在 `STRING` 节点；输出 PASS/FAIL 列表。这只是本地合规检查，**不等于**真实 API 验证，汇报中不得声称验证过 Gemini 行为。
  3. `tools/diag_council.py` 在 HTTP 4xx 时打印脱敏后的 `error.message`（F1 已能解析）。
- 验收（单元测试）：打桩 `urlopen`，第一次返回 400 且消息含 "response_schema"，断言第二次请求体不含 `responseSchema`；第二次成功则整体成功；非 schema 相关的 400 不降级。
