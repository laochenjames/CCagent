# 实施方案 v2.1：清单保存卡顿优化 + 仪表盘吸顶

本文档是对 v2 的**小幅优化补丁**，交给 AGENT 执行。范围只有两件事：(1) 修复补清单时的卡顿；(2) 顶部打分框吸顶。除此之外不要改动评分模型、API 语义和 LLM 调用。

## 0. 问题诊断（基于对 `app.js`、`server.py`、`store.py`、`score.py` 的阅读，未做实测）

用户反馈：填清单时很卡，怀疑与"自动提交"有关。自动提交本身没有问题，**问题出在它的接线方式**。按影响从大到小：

1. **每次保存都整表重建。** `scheduleFieldUpdate` 成功后调用 `renderResult(data)`，其中 `renderGroups` 先 `container.innerHTML = ""` 再重建所有行。后果：
   - 用户在 A 框按 Tab 跳到 B 框，A 的 `change` 触发保存；响应回来（几百毫秒后）整表重建，**B 框被销毁，焦点丢失，B 里已输入的字符直接消失**。
   - 每次保存滚动位置和焦点都可能跳动，体感就是"卡"。
2. **每次保存后分组被重新排序。** `build_groups` 按"可提升量"降序，前端每次重绘都套用，导致用户正在填的那一组**随着 gain 下降而跳到下方**，行在鼠标下面移动。
3. **共用一个防抖计时器，会丢更新。** `debounceTimer` 全局唯一，`clearTimeout(debounceTimer)` 会把 400ms 内另一个字段的待发送内容直接丢弃。快速连续改两项，前一项根本没保存，对勾也不出现。
4. **服务端并发读改写，会互相覆盖。** `_handle_fields_update` 读取整份字段状态、修改、整体写回，`ThreadingHTTPServer` 是多线程；两个请求并发时，后写的会覆盖先写的（丢更新）。
5. **时机设计拖慢反馈。** 数字框只在 `change`（失焦）时保存，输入时没有任何反馈；单选和开关点了也要再等 400ms 防抖。
6. **服务端次要开销。** 每次请求都重新读取并解析 `fields_career.json`；SQLite 使用默认日志模式，每次提交都要同步落盘（Windows 上可能几十毫秒）；HTTP/1.0 每个请求新建连接。这些单项都不大，但叠加后会增加延迟，修起来也很便宜。

**目标体验：** 填完一项，仪表盘在约 300ms 内更新；Tab 切换和连续输入时焦点不丢、内容不丢、页面不跳。

## 1. 前端改动（`app.js`，必要时 `index.html`、`style.css`）

### 1.1 拆分渲染：整表渲染 与 局部更新
保留 `renderResult(data)`，仅用于：首次体检、追加文字（append-text）、打开历史会话。它做整表渲染。

新增 `applyFieldsResult(data)`，用于**每次保存成功后**，只做局部更新：
1. `renderDashboard(data)`、`renderFlags(data.flags)`（这两个本来就只改文本和样式，无需改动）。
2. 更新各分组标题行的状态文字和 `gain` 文字（按分组 id 查找已有 DOM，原地改 `textContent`）。
3. **对账（reconcile）**：
   - 分组或字段的"适用性"变化（例如把 `needs_cash` 改成"否"后，财务安全垫整组消失）：按 id 增删对应 DOM。新出现的组按下面规定的规范顺序插入到合适位置；消失的组或行直接移除。
   - 对仍然存在的行，只在**该行当前没有焦点且该字段没有待发送的修改**时，用服务端返回值校正控件状态（单选/开关的 active 样式、skipped 样式、"不太确定"勾选）。**不要覆盖正在输入的 input**。
4. **不重排分组。** 分组顺序在 `renderResult` 整表渲染时确定（按服务端返回顺序），之后只按 id 原地更新。规范顺序用于插入新出现的组：基本情况、变现与需求、时间与执行、划算程度、财务安全垫、止损设置。
5. 不使用 `innerHTML = ""` 清空清单容器。

实现要点：整表渲染时给每个组和行打上 `data-group-id`、`data-field-id`，并维护 `rowRefs = Map(fieldId → {row, controls})`，局部更新直接通过这个 Map 找元素。

### 1.2 保存队列（替换 `scheduleFieldUpdate`）
去掉全局 `debounceTimer` 和 `updateSeq`。使用**合并队列 + 单飞（single-flight）**：

```js
const pending = {            // 待发送内容，按字段合并，同一字段只保留最新值
  fields: new Map(),         // fieldId -> {id, value, unsure}
  skip: new Set(),
  unskip: new Set(),
  ticks: new Set(),          // 需要显示对勾的行
};
let inFlight = false;
let flushTimer = null;

function queueUpdate(op, delayMs) {
  // op: {field:{id,value,unsure}} 或 {skip:id} 或 {unskip:id}
  // 把 op 合并进 pending；skip/unskip 与同字段 field 互相覆盖（后到者生效）
  // 然后 schedule flush: clearTimeout(flushTimer); flushTimer = setTimeout(flush, delayMs)
}

async function flush() {
  if (inFlight) return;                 // 在途请求期间只累积，不并发发送
  if (nothingPending()) return;
  const payload = takePending();        // 取走并清空 pending
  inFlight = true;
  setSyncState("updating");
  try {
    const res = await fetch(`/api/sessions/${currentSessionId}/fields`, {...});
    const data = await safeJson(res);
    if (!res.ok) { showRowError(payload, data.error); }
    else { currentResult = data; applyFieldsResult(data); showTicks(payload); }
  } catch (err) { showRowError(payload, err.message); }
  finally {
    inFlight = false;
    setSyncState("idle");
    if (!nothingPending()) flush();     // 期间累积的修改，请求结束后立即再发一次
  }
}
```

要点：
- **同一时刻最多一个在途请求**，因此不需要 `seq` 乱序保护，也不会产生服务端并发覆盖（这是客户端侧的第一道防线）。
- 保存失败时：保留用户输入，在该行显示行内红色错误，**不要**调用整表渲染，不要弹窗。
- 保存成功时：只在被保存的行显示对勾（1.5 秒后淡出）。

### 1.3 触发时机
| 控件 | 触发 | 延迟 |
|---|---|---|
| 单选芯片、是/否、"不太确定"开关、"没概念"/"撤销跳过" | 点击即触发 | 0ms（直接 flush） |
| 数字、文本输入框 | `input` 事件 | 600ms 防抖（每次输入重置） |
| 数字、文本输入框 | `change`（失焦）或按 Enter | 立即 flush（取消防抖等待） |
| 数字输入为空字符串 | 不提交 | — |

`past_projects` 子表单（如实现了多输入）：与文本框同样处理，合并成一个字段值一次提交。

### 1.4 乐观 UI
- 用户的输入以输入框/芯片当前状态为准，**不等服务端回显**。
- 仪表盘区域在保存期间只显示一个很轻的"更新中…"小字（置信度旁），**不要**用骨架屏，**不要**禁用任何输入控件。

### 1.5 仪表盘吸顶

**HTML 结构：** 保持 `dashboard-card` 为 `#result-section` 的第一个子元素，不要放进有 `overflow` 的容器内（sticky 失效）。

**CSS：**
```css
html { scroll-padding-top: 96px; }          /* 聚焦/滚动到输入框时，不被吸顶条遮住 */
.dashboard-card {
  position: sticky; top: 0; z-index: 50;     /* 低于抽屉(100)和弹窗(200) */
  background: var(--card);
  transition: padding 0.2s ease, box-shadow 0.2s ease;
}
.dashboard-card.stuck { box-shadow: 0 4px 14px rgba(0,0,0,0.08); }

/* 紧凑模式：滚动后收成一条窄栏 */
.dashboard-card.compact { padding: 8px 14px; }
.dashboard-card.compact .headline,
.dashboard-card.compact .gauge-zones,
.dashboard-card.compact .conf-note,
.dashboard-card.compact .marker-hint,
.dashboard-card.compact #score-range { display: none; }
.dashboard-card.compact .score-label { font-size: 18px; }
.dashboard-card.compact .score-action { margin-top: 0; font-size: 13px; }
.dashboard-card.compact .dash-top { align-items: center; flex-wrap: nowrap; }
.dashboard-card.compact .gauge-wrap { margin: 8px 0 0; }
.dashboard-card.compact .gauge-track { height: 10px; }
.dashboard-card.compact .gauge-marker { height: 16px; top: -3px; }
```
紧凑模式下总高度目标 ≤ 80px（桌面）、≤ 96px（手机）。手机上把 `.dash-right` 设为 `min-width: 0` 并允许缩小。

**JS（带滞后，防止临界处抖动）：**
```js
const dash = document.querySelector(".dashboard-card");
let dashTop = 0;                      // 首次渲染后记录：dash.getBoundingClientRect().top + window.scrollY
let ticking = false;
function updateStuck() {
  const y = window.scrollY;
  const compact = dash.classList.contains("compact");
  if (!compact && y > dashTop + 120) dash.classList.add("compact");
  else if (compact && y < dashTop + 40) dash.classList.remove("compact");
  dash.classList.toggle("stuck", y > dashTop);
  ticking = false;
}
window.addEventListener("scroll", () => { if (!ticking) { ticking = true; requestAnimationFrame(updateStuck); } }, { passive: true });
```
- `dashTop` 在**非紧凑状态**下的首次渲染完成后计算；`renderResult` 整表渲染后重新计算一次（输入区从展开变折叠会改变位置）。
- 两个阈值（120 进入、40 退出）构成滞后区间，避免高度变化引起的反复切换。
- 页面滚回顶部时自动恢复完整仪表盘。

## 2. 服务端改动

### 2.1 `server.py`
1. **按会话加锁，保证读改写原子。** 模块级 `_session_locks = defaultdict(threading.Lock)`（再用一个全局小锁保护字典本身）。`_handle_fields_update`、`_handle_append_text` 中从读取会话到写回数据库的整段放进该会话的锁内；`_handle_analysis` 的 `save_analysis` 同理（LLM 调用本身不要放在锁内，避免长时间占用锁；只对读取与写回加锁）。
2. **缓存注册表与智囊库。** `llm.load_fields_registry()`、`llm.load_advisors_library()` 改为带 mtime 检查的内存缓存：文件未改动时直接返回缓存对象（返回只读使用，勿在调用方修改；如需修改先 deepcopy）。
3. **HTTP/1.1 保持连接。** `AppHandler.protocol_version = "HTTP/1.1"`；`ThreadingHTTPServer` 子类设置 `daemon_threads = True`。确认所有响应（含错误响应、静态文件）都带 `Content-Length`（目前已具备）。静态文件加 `Cache-Control: no-cache`。
4. **返回服务端耗时。** `/api/sessions/{id}/fields` 的响应对象加 `server_ms`（整数毫秒，从进入 handler 到响应构造完成）。仅用于调试，前端用 `console.debug` 输出该值与整次往返耗时。
5. 字段更新路径中的 `copy.deepcopy`（`build_groups` 的 gain 模拟）如实测占用明显，可改为浅拷贝加就地覆盖后恢复；**先不要优化，除非 `server_ms` 显示服务端耗时 > 100ms。**

### 2.2 `store.py`
- `get_db` 或 `init_db` 中设置：`PRAGMA journal_mode=WAL;`（持久属性，只需在初始化时设置一次）；每个连接设置 `PRAGMA synchronous=NORMAL;`。
- 不要改动表结构。保持单连接/单请求的使用方式。

### 2.3 不要改动的内容
`score.py` 的模型与常量、`engine.py` 的规则、LLM 调用与 prompt、API 路径和请求/响应字段语义（只新增 `server_ms`）。

## 3. 测试与验收

### 3.1 自动测试（新增，不依赖网络）
- `test_server_fields.py`：启动测试用服务实例（临时数据库），用两个线程**同时**对同一会话提交不同字段，结束后读取会话，两个字段**都必须存在**（验证会话锁）。
- 断言 `/fields` 响应含 `server_ms`，且整个路径无 LLM 调用（沿用 v2 的 mock 断言）。
- 缓存：连续两次 `load_fields_registry()` 在文件未改时返回同一对象；修改文件后下一次返回新内容。
- 既有测试全部仍通过。

### 3.2 手动验收（逐条勾选，结果记入 `tests/golden/RESULTS.md`）
1. 在清单里用键盘 Tab 连续填 5 个数字框，每个框输入后直接 Tab：**所有值保留，焦点连续前进，没有任何一次丢焦点或输入被清空**。
2. 填写过程中，分组**不会换位置**；各组右侧的"+N%"原地变化。
3. 快速点击多个单选/开关：每一项都保存，对勾逐项出现；刷新页面后从历史会话打开，所有值都在。
4. 填完一项后，仪表盘在约 300ms 内变化（开发者工具里 `server_ms` 一般应为个位数到几十毫秒，浏览器往返一般 < 150ms）。
5. 把"需要花钱吗"和"会占用主业时间吗"都改为否：财务安全垫整组消失；改回后重新出现，位置合理，输入过的值仍在。
6. 向下滚动：仪表盘吸在顶部，约滚动 120px 后收成窄栏（标签、行动词、置信度、迷你刻度条）；滚回顶部恢复；聚焦清单中任一输入框，**不被吸顶条遮挡**；在滚动临界区来回滚动，**无抖动闪烁**。
7. 手机宽度（≤ 640px）下吸顶栏不超过约 96px 高，清单仍可正常操作。
8. 在服务端人为制造一次失败（例如临时让接口返回 500）：该行显示行内错误，输入内容保留，页面不重绘。
9. 打开两个浏览器标签同时编辑同一会话的不同字段，两处修改都不丢（会话锁生效）。

### 3.3 如果优化后仍觉得慢
先看服务端日志里 `fields_update ... ms=`，以及浏览器控制台输出的往返耗时：
- 服务端耗时 > 100ms：再考虑优化 gain 模拟（见 2.1 第 5 项）与数据库写入。
- 服务端耗时很小但往返很长：检查是否通过 `localhost` 访问（Windows 上可能先走 IPv6 再回退），改用 `http://127.0.0.1:8100`，并把这一点写进 README。
