# 实施方案 v2：杀毒软件式"职业投入体检"

本文档是对 v1 的**改版方案**，交给 AGENT 执行。v1 的规则引擎、抽取校验、lint、存储保留；**交互与结论呈现整体改版**。路径均相对于 `E:\Doc\Python_daye\CCagent\`（当前代码所在的根目录；v1 文档中的 `agent2/` 前缀已作废）。

## 0. 为什么改

v1 的实际体验是：输入 → 等 10–30 秒 → 一份很长的报告（双轴、档位、数据质量、7 位智囊、批判、验证设计……）→ 填补全表单 → 点按钮 → 再等 10–30 秒。用户要的不是这个。

用户要的是**杀毒软件那种体验**：
- 输入一句话，几秒内就有一个**模糊但直观的判断**；
- 同时给一个**置信度**，信息越多置信度越高；
- 下面**一次性列出所有可以补充的项目**，想填哪个填哪个，**填一项，评分和置信度立刻变化**，不用点"提交"，不用再等 LLM；
- 详细分析是可选的，点了才出。

## 1. 产品形态

### 1.1 单屏结构（自上而下）
1. **输入区**：文本框 + "开始体检"按钮。体检后收起成一行"你的描述 ▸ 修改"。
2. **仪表盘**（核心，首屏必须一眼看懂）：
   - 一条 0–100 的横向刻度条，上面有**一个标记点（评分）和一段阴影区间（可能范围）**；区间宽度随置信度变化，信息少时几乎铺满，信息多时收窄。
   - 刻度条下方三个区段文字标注：偏低 / 一般 / 偏高（不得只靠颜色区分）。
   - 评估词（大字）：偏低 / 一般 / 偏高 / 还看不出来；右侧是**置信度 N%**（进度条）。
   - 一句话结论（代码模板生成，见 6.4）。
   - 评分数字用小字显示区间（如"可能范围 24–88"），**不要把单个分数做成主视觉**，避免用户把它当成概率或预测。
3. **风险条**：显示"发现 N 个风险"，红/黄徽标，点击展开风险文案（沿用 v1 `compute_flags`）。无风险时显示"未发现明确风险（不代表没有风险）"。
4. **提升准确度清单**：按分组一次性列出**所有适用的项目**（见第 5 节），每组一个标题行，标题行右侧显示"补全可提升置信度约 +N%"。每个项目一行，行内直接是控件（芯片/开关/小输入框），改动即保存。
5. **详细分析**（折叠，默认收起）："查看详细分析（约 10–20 秒）"按钮，点击后才调用 LLM。内容：各智囊的评级与依据、假设批判、两周内可验证的 3 件事、验证设计。
6. 固定免责声明。

页面右上角保留"历史会话""设置"。

### 1.2 交互细节
- 控件改变 → 400ms 防抖 → 请求 `/api/sessions/{id}/fields` → 仪表盘动画过渡（标记点和区间 400ms 平滑移动，置信度条同步）。无"提交/重新评估"按钮。
- 每个项目行右侧两个小控件：**"不太确定"开关**（打开后该项按"猜测"处理，区间变宽）和**"没概念"链接**（置灰为"已跳过"，可撤销）。**不再有"来源三选一"**。
- 有含糊项（LLM 回译的 ambiguous）：该行显示黄色提示条与回译问题，用户重新输入即可。
- 所有项目都是可选的，**不得有任何必填、阻断或强制引导**。涉及隐私的项目（现金、借贷等）旁边显示小字"涉及隐私，可不填"。
- 置信度旁固定小字："置信度表示信息够不够，不表示结论一定对。"
- 评估中使用骨架屏，不要出现纯文字等待。

## 2. 速度与 LLM 分工

| 动作 | 是否调用 LLM | 目标耗时 |
|---|---|---|
| 首次体检（自由文本 → 字段） | 是，**只做抽取**（`prompts/extract_prompt.md`） | 5 秒内为目标 |
| 填写/修改/跳过某项 | **否，纯代码重算** | 服务端 < 300ms |
| 追加一段文字（可选入口） | 是，只做抽取，已锁定字段不变 | 5 秒内为目标 |
| 详细分析 | 是，按需（`prompts/analysis_prompt.md`） | 10–20 秒 |

- 抽取调用可使用更快的模型：`.env` 新增可选 `GEMINI_FAST_MODEL`，缺省与 `GEMINI_MODEL` 相同。
- 详细分析结果缓存；任何字段变化后，缓存标记为过期（`stale=true`），页面显示"基于较早的信息，点击更新"。
- 追加文字入口：仪表盘下方一个小输入框"再补充一段话（可选）"。

## 3. 评分模型（新增 `score.py`，纯函数，无 I/O）

### 3.1 因子与权重
复用 v1 `engine.py` 的 5 个评级函数（`rate_monetization` 等），评级转换为评分点：

| 因子 | 权重 | 关键字段（用于覆盖度） |
|---|---|---|
| MONETIZATION | 3 | paid_evidence, precedent |
| EXECUTION | 2 | weekly_hours_actual_recent, weekly_hours_planned, continuity_weeks_12m, past_projects |
| OPPORTUNITY | 2 | unit_price, take_home_ratio, floor_take_home_per_unit（或 floor_price_client 作为到手底线的替代） |
| SAFETY_NET | 2 | cash_free, monthly_expense, cash_outlay, borrowing_or_essential_funds（仅统计适用字段） |
| STOPLOSS | 1 | first_paid_month, validation_months, will_really_stop |

- 评级 → 评分点：高 = 0.85，中 = 0.55，低 = 0.20。
- 评级为"无法判断"→ 该因子**未知**。
- 评级为"不适用"（如纯时间项目的 SAFETY_NET）→ 该因子移出，**其余权重重新归一**。
- `purpose=learn`：移出 MONETIZATION 与 OPPORTUNITY，结论文案改用"学习型：按试错成本与坚持度评估"。
- 权重和评分点均为**经验值**，写成 `score.py` 顶部的常量，注释标明。

### 3.2 每个因子的区间
- **已知因子**：以评分点 p 为中心，半宽 = 证据半宽 + 覆盖度附加半宽，再裁剪到 [0.15, 0.95]：
  - 证据半宽取该因子**已提供的关键字段中最差的类别**：事实 0.00、自报 0.05、估计 0.10、猜测 0.18。`ambiguous`、`skipped`、`missing` 的字段不算已提供。
  - 覆盖度附加半宽 = 0.15 × (1 − 覆盖度)，覆盖度 = 已提供的关键字段数 ÷ 适用的关键字段数。
- **未知因子**：区间 [0.15, 0.95]，点估计 0.55（"中"）。

### 3.3 合成
设归一化后的权重为 w_i（所有适用因子之和为 1）：
- 评分点 = 100 × Π p_i^w_i
- 区间下界 low = 100 × Π lo_i^w_i；上界 high = 100 × Π hi_i^w_i
- 这是**加权几何平均**：成功需要多个条件同时成立，任何一个因子很弱都会明显拉低整体。因为函数对每个因子单调，区间合成是有效的。
- 数值取整只在输出层做，计算保持浮点。

### 3.4 置信度
- 置信度 = 1 − (high − low) ÷ 80，限制在 [0, 1]（80 是所有因子均未知时的区间宽度：95 − 15）。
- 展示上限 95%（永远不显示 100%）。
- 置信度由区间宽度**导出**，没有单独的规则：猜测多、覆盖度低，区间自然变宽，置信度自然降低。

### 3.5 红线
`compute_flags` 中的红色风险里，以下三类触发红线：借贷或动用必需资金、生存月数 < 3 且需要花钱、花费占现金 > 25%。触发后：`high = min(high, 25)`，`low = min(low, high)`，评分点 = min(评分点, high)，评估词强制为"偏低"，行动词为"不建议"。
（止损线过早的红色风险**不触发红线**，只显示在风险条里。）

### 3.6 评估词与行动词（代码模板）
- 置信度 < 0.25：评估词 = "还看不出来"，行动词不显示。
- 否则按评分点：< 35 → "偏低"；35 到 65 → "一般"；≥ 65 → "偏高"。
- 行动词（置信度 ≥ 0.25 时显示）：
  - 触发红线 → "不建议投入"
  - 偏低 → "目前不太划算，除非能改善下面几项"
  - 一般 → "适合先小额试验"
  - 偏高 → "值得认真推进验证"（**不再有"可加大投入"**：自报数据不足以支持加大投入的结论）
- 置信度 < 0.5 时，一句话结论前加"初步看法："。
- 固定追加："这是基于你提供的信息的大致判断，不是精确数字。"

### 3.7 分组"可提升"估算
对每个分组：把该分组内**当前缺失的关键字段**用 `neutral_value`（见 5.1，仅要求能让该因子得出确定评级）、类别"自报"代入，重新计算置信度，差值即"补全可提升置信度约 +N%"（取整，最小显示 1%；已补全的分组不显示）。此计算只用于展示，不写入存储。分组内字段只有部分缺失时同样适用。

### 3.8 输出
```
score: { point, low, high, label, action, confidence, confidence_note }
factors: [ {id, name, rating, rule_note, known(bool), interval:[lo,hi]} ]
```
`label`/`action` 见 3.6；`point/low/high` 取整到整数。

### 4.1 `engine.py`

- 旧的 `career_council_prompt.md` 保留在 `prompts/` 但不再使用（可在 README 注明已被拆分取代）。
- 错误分类与重试沿用 v1。

### 4.3 `verify.py`
- 抽取校验（quote 子串、数字可追溯、类别降级、锁定字段保护）：**保持不变**，应用于 extract 结果。
- 输出 lint（数字白名单、违禁措辞、阈值标注、AI 提示标注）：应用于 analysis 结果。数字白名单集合 = 用户输入中的数字 ∪ 已知字段数值 ∪ 程序评级文案中的数字 ∪ `NUMBER_WHITELIST`。

### 4.4 `server.py` 与 `store.py`

API：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/evaluate` | body `{text}` → 创建会话 → extract → 引擎评分 → 返回 result |
| POST | `/api/sessions/{id}/fields` | body `{fields:[{id,value,unsure}], skip:[field_id], unskip:[field_id]}` → **纯代码**更新字段并重算，返回 result。禁止调用 LLM |
| POST | `/api/sessions/{id}/append-text` | body `{text}` → extract（已锁定字段不变）→ 合并 → 返回 result |
| POST | `/api/sessions/{id}/analysis` | 调用 analysis，lint 后缓存，返回 `{analysis, stale:false}` |
| GET | `/api/sessions/{id}` | 返回 result 及 `analysis`（若有）与 `stale` |
| GET | `/api/sessions`、DELETE `/api/sessions/{id}`、`/api/config`、`/api/save-config`、`/api/test-connection`、`/api/advisors`、`/api/fields` | 沿用 v1 |

- 旧的 `/api/sessions/{id}/supplement` 删除。
- 字段更新语义：表单提交的字段 `source=form`；`unsure=true` → category=猜测，否则 category=自报；该字段状态设为 given。`skip` → `status=skipped`；`unskip` → `status=missing`。表单字段不得被后续 extract 覆盖（沿用 v1 锁定规则）。
- `ask_count` 机制**取消**（清单是静态的，不再有"问满 2 次"）。
- 存储：字段编辑**更新最新一条 evaluation 记录**，不新增版本；只有 `append-text` 新增版本。`analysis_json` 与 `stale` 存在 evaluation 记录上（可新增列，需向后兼容旧库：启动时检查列是否存在并 `ALTER TABLE`）。

### 4.5 result 对象（新）
```
{ session_id, version, decision,
  score: {...}, factors: [...],
  flags: [ {level, text} ],
  groups: [ { id, name, state: "已评|部分|未评|不适用", gain, fields: [
      {id, ui_label, type, unit, choices, item_fields, value, status, unsure, sensitive, clarify} ] } ],
  headline,
  clarify: [...],
  analysis: null | {...}, analysis_stale: bool,
  lint: {dropped: [], hidden_count},
  disclaimer }
```
分组按 `gain` 降序排列，"基本情况"组固定排第一且没有 gain。已补全且 `gain` 为 0 的组排最后。适用性由 `is_field_applicable` 决定，不适用的字段不出现在 `groups` 里。

## 6. 前端（重写 `index.html` / `app.js` / `style.css` 的主视图）

沿用现有 Editorial 极简风格和历史、设置弹窗。移除：完整度条、数据质量徽标、档位徽标、双轴格、补全卡、版本对比、智囊会诊/批判/验证设计的默认展示、来源三选一、"补充后重新评估"按钮。

### 6.1 仪表盘实现要点
- 刻度条：容器宽 100%，高约 14px；阴影区间 `left = low%`，`width = high − low`；标记点 `left = point%`。三个区段（0–35、35–65、65–100）用文字标注在条下方。使用 CSS transition 400ms。
- 区间宽度很大（置信度很低）时，标记点旁显示"位置仅供参考"。
- 评估词为"还看不出来"时，标记点隐藏，只显示区间。
- 置信度用文字 + 进度条，数字不要比评估词更醒目。

### 6.2 清单实现要点
- 一个分组一个区块，标题行含分组名、状态（已评/部分/未评）、右侧"+N%"。
- 项目行：左标签，中控件，右"不太确定"开关与"没概念"链接。
- number 控件使用 `inputmode="decimal"`，空值不提交；blur 或 change 时触发保存；保存成功显示轻微对勾，失败显示行内错误，不弹窗。
- 请求乱序保护：每个会话维护一个递增的 `seq`，只应用最新响应。
- 详细分析区：按钮 → loading → 渲染。渲染内容：因子表（名称、评级、rule_note）、智囊依据与提示、假设批判、两周验证、验证设计；`analysis_stale=true` 时在区块顶部显示"基于较早的信息，点击更新"。

### 6.3 前端不得计算评分、评级或风险，一律使用服务端返回值。

### 6.4 一句话结论模板
- 置信度 < 0.25："目前信息太少，还看不出来。把下面几项补一补，判断会更有依据。"
- 红线："综合来看，现阶段**不建议**投入。原因：{reasons}。"
- 其余："{前缀}{评估词}——{行动词}。"（前缀按 3.6 规则）

## 7. 测试与验收

### 7.1 单元测试（`python -m unittest discover tests`，不依赖网络）
更新 `tests/test_engine.py`：删除已移除函数的用例；保留 `rate_*` 与 `compute_flags` 的用例。新增 `tests/test_score.py`：
1. **全部未知**（所有因子均未知）：low = 15，high = 95，point = 55，confidence = 0。
2. **单调性**：对任意字段状态，补充一个字段（类别同为自报），区间宽度不增加、置信度不降低；把同一字段的类别从自报改为猜测，区间宽度不减少。
3. **证据半宽**：同一取值下，事实 < 自报 < 估计 < 猜测的区间宽度严格递增。
4. **覆盖度**：同一因子下，已提供的关键字段越多，附加半宽越小。
5. **红线**：借贷、生存月数 < 3、花费占比 > 25% 任一触发时，high ≤ 25，评估词为偏低，行动词为不建议；止损线过早只出风险提示，不触发红线。
6. **不适用与重新归一**：纯时间项目时 SAFETY_NET 被移出，权重之和为 1。
7. **purpose=learn**：MONETIZATION 与 OPPORTUNITY 移出。
8. **置信度上限**：所有字段均填为自报时，置信度 ≤ 95%；全部为事实且覆盖完整时，仍不显示 100%。
9. **gain 估算**：已补全的分组 gain 为空；缺失分组 gain > 0；gain 之和不要求等于总提升。
10. **评估词边界**：置信度 0.25 前后；评分点 35、65 前后。

`tests/test_verify.py` 保持，补充：数字白名单包含程序评级文案中的数字。
