# 实施方案 v2.3.2：v2.3.1 审阅后的最小补丁

背景：v2.3.1 的 7 个必做项已落地，35 项测试通过。审阅发现 4 处与方案不符或会在真实使用中出问题的地方，本方案只处理这 4 处加 1 个小测试，不扩大范围。

原则同 v2.3.1：先写测试再改代码；不得为让评分更好看而改任何阈值；前端不计算评分。
交回：改动文件清单、`python -m unittest discover tests -v` 输出、`python tools/calibrate.py` 输出（四项硬性验收不得变化）、第 3 节勾选结果。

## 1. 必做

### 1.1 历史列表的"红线"标识实际不生效
**现象**：`app.js` 的历史列表用 `s.action === "不建议投入"` 判断红线，但 `store.list_sessions` 返回的条目里没有 `action`（只有 id、title、updated_at、version、label、confidence_pct），所以条件恒为假，红线会话仍显示"偏低 · 置信度 X%"。

**做法**：
- `store.list_sessions`：每个条目增加 `red_line`（布尔）。取值：结果里有 `score.red_line` 就用它；没有（v2.3.1 之前保存的结果）时，回退为 `score.action == "不建议投入"`。
- `app.js` 历史列表：改用 `s.red_line` 判断，显示"偏低 · 红线"；不再比较 label 和 action 字符串。
- 测试：构造三条结果（有 `red_line:true`、有 `red_line:false`、无 `red_line` 但 `action` 为"不建议投入"），断言 `list_sessions` 返回的 `red_line` 分别为 True、False、True。

### 1.2 `llm.call_gemini` 可能返回 None
**现象**：循环固定两次。若第一次遇到 429（睡 2 秒后继续），第二次又遇到 400 且带 `thinkingConfig`，代码去掉参数后 `continue`，循环结束，函数落到末尾隐式返回 None，调用方 `llm_raw.get(...)` 抛 AttributeError，页面显示 500。免费档 429 并不罕见。另外，去掉 thinkingConfig 的那次重试占用了本来留给 429/5xx 的重试次数。

**做法**：
- 函数在任何情况下都不得返回 None：循环结束后必须抛 `GeminiAPIError("请求失败", "多次重试后仍失败")`。
- "去掉 thinkingConfig 重试"不计入 429/5xx 的重试次数（用独立标志，或把循环放宽到 3 次并明确每种情况各自最多一次）。
- 模块级变量记住"模型不接受 thinkingConfig"，之后的请求不再带这个参数，避免每次请求都多一次必然失败的往返。该变量只在进程内有效，重启后重新探测。
- 测试（mock `urllib.request.urlopen`）：
  - 序列 [429, 400(含 thinkingConfig), 200]：最终返回正常数据；
  - 序列 [500, 500]：抛 `GeminiAPIError`；
  - 序列 [400(含 thinkingConfig), 200]：返回正常数据，且第二次请求体不含 `thinkingConfig`；
  - 之后再调用一次：请求体不含 `thinkingConfig`。

### 1.3 红线时，页面和报告里仍留着"置信度"字样
**现象**：
- 页面：`conf-pct` 在 `<span>置信度 <strong id="conf-pct">` 里面，红线时显示为"置信度 由规则直接判定（红线）"，读起来别扭；"置信度表示信息够不够……"那行说明也还在。
- 下载的 HTML 报告摘要和 Markdown 报告摘要仍输出"置信度 20%"，与"不建议投入"并列。

**做法**：
- 页面：红线时把"置信度"标签、百分比、进度条、说明行整体替换为一行"由规则直接判定（红线）"；非红线时恢复。
- HTML 报告摘要、Markdown 报告摘要：`score.red_line` 为真时，不输出"置信度 X%"，改输出"由规则直接判定（红线）"；"可能范围"保留。
- 测试：红线结果的 HTML 报告和 Markdown 报告中不含"置信度 "后跟百分比的文字，含"由规则直接判定"；非红线结果的行为不变。

### 1.4 Markdown 报告缺少"评分未包含"提示
**现象**：v2.3.1 只在 HTML 报告里加了"评分未包含：……（若计入将评为低）"，Markdown 报告没有任何排除提示，用户下载的 Markdown 里分数看不出有因子被排除。

**做法**：在 `build_markdown` 的第 1 节摘要末尾和第 4 节评分依据表后，各加一行"评分未包含：……"，规则与 HTML 一致（`rating_if_included == "低"` 时附"（若计入将评为低）"，否则只写名称）。
- 测试：手动排除一个本应评"低"的因子，Markdown 报告含"评分未包含"和"若计入将评为低"。

### 1.5 补一个输入长度测试
v2.3.1 的 2000 字上限只有手动验收，没有自动测试。
- 测试：`/api/evaluate` 和 `/append-text` 提交 2001 字返回 400；恰好 2000 字不因长度被拒（mock LLM）。

## 2. 可选（不阻断上线）

- `score.FACTOR_KEY_FIELDS["EXECUTION"]` 仍包含 `past_projects`，但该字段已设为 `ui_show:false`，用户无法在清单里填写，因此覆盖度永远算不满（约多出 0.04 的半宽）。建议覆盖度只统计 `ui_show` 为 true 的字段。**注意**：这会让校准输出的数字略有变化，改后必须重跑校准并确认四项硬性验收不变。
- 用户清空字段后，该字段会以 `source: "form"` 的 `missing` 状态保存，之后"补充抽取"不会再覆盖它。这是有意的（用户明确清空了），但页面上没有任何提示。若不想这样，改为直接删除该字段记录。需要时再决定。
