# 实施方案 v2.4.5：上线前的两处小修

背景：v2.4.4 代码复核后没有发现阻断上线的缺陷，只有两处建议在上线前改掉，改动都很小。

原则：先写测试再改代码；不改评分规则；日志和错误信息不含用户文字和任何 Key。
**汇报要求**：逐条对照编号写"已完成 / 未完成 / 偏离"。

## 1. 托管 Key 出错时，不向用户透传厂商细节

**问题**：v2.4.4 把厂商 4xx 的错误信息附在提示后面。对用户自带的 Key 这是对的；但免费额度走的是运营者的托管 Key，托管 Key 出问题（账单用完、被限流、被停用）时，用户会看到"API Key 无效或无权限，请检查配置（厂商返回：……）"。这既误导（用户没有配置可检查），也可能暴露运营者账号信息（项目编号、账单状态）。

**做法**（`evaluate`、`append-text`、`analysis` 三个端点一致）：
- 托管模式下、没有使用自带 Key 的调用，捕获 `LLMError` 后：
  - 返回 HTTP 503，`category` 为"服务暂不可用"，`error` 为固定文案"免费服务暂时不可用，请稍后再试，或在设置中使用你自己的 Key。"；
  - 服务端日志仍记录原始的 `category` 与状态码（不含厂商返回的正文）；
  - 额度退还逻辑不变。
- 自带 Key 的调用、以及非托管模式，保持现状（带厂商返回的细节）。
- 前端：收到 `category` 为"服务暂不可用"时，显示该文案，并在错误提示旁提供"打开设置"的入口。
- 测试：托管模式、无自带 Key，mock 一个带"（厂商返回：secret detail）"的 `LLMError`，断言响应体不含 `secret detail`、状态码为 503、额度已退还；带自带 Key 时，响应体含该细节；非托管模式含该细节。

## 2. 未经真实 Key 验证的厂商，在界面上标注

**问题**：xAI 默认模型和 DeepSeek 的抽取、分析流程都还没有用真实 Key 跑通（xAI 的 403 原因未明，DeepSeek 账号余额为 0）。在核实之前，应该让用户知道。

**做法**：
- `index.html`：下拉选项改为"Grok（xAI）· 测试中"和"DeepSeek · 测试中"，Gemini 不加标注。
- 下拉框下方增加一行小字："Grok 与 DeepSeek 仍在测试中。如果'测试连接并自测'失败，请改用 Gemini，或稍后再试。"
- 等真实 Key 核实通过后，再去掉"测试中"标注（这一步不在本方案内）。
- 烟雾测试：断言这两个选项的文字含"测试中"，Gemini 选项不含。

## 3. 验收

### 自动
- `python -m unittest discover tests -v` 全部通过；`python tools/calibrate.py` 四项硬性验收不变；`npm test` 全部通过。

### 手动（HOSTED=1，在本机用托管的 Gemini Key 跑一遍，约 10 分钟）
1. 页面控制台无报错；顶栏显示"今日免费额度 10/10"。
2. 评估一次：额度变为 9/10；改一个字段：额度不变；补充抽取一次：8/10；详细分析一次：7/10；下载 HTML 和 Markdown 都正常。
3. 另开一个无痕窗口：看不到上一个窗口的历史会话。
4. 在设置里选择 Grok 或 DeepSeek，确认看到"测试中"标注和说明。
5. 把托管 Key 临时改成一个无效值重启，评估一次：看到"免费服务暂时不可用"，额度不减少；改回后恢复。
