# agent2 实施方案 v1：职业投入快评工具

本文档交给 AGENT 执行。已由 Claude 与用户讨论确认：产品形态、智囊团、双轴结论、v1 只做本机跑通。

## 0. 目标与边界

### 产品形态
用户在一个输入框里自由描述"想做的事"，不要求带数字。系统立即给出一个**大致评估**，并指出**最该补充的 3 项数据**；用户补充后重新评估，结论逐步更准确。

流程：快评 → 补全 → 重评。（精评层，即反推门槛、盈亏翻转点、三套情景值，在 v1.1 实现，本期不做。）

### 核心原则（来自 agent2/career 的 v1.0 提示词，必须保持）
1. **不编造关键数字。** 数字只能来自用户原话或用户补全；缺失就是缺失。
2. **评级、双轴结论、行动档、完整度、数据质量全部由代码按规则计算**，LLM 不打分、不给档位。
3. **"无法判断"是合法输出。** 信息不足时不硬给结论。
4. 批判针对假设和数据，不对人做性格、动机、习惯推断。
5. 不做规则兜底。与 CCagent 不同：LLM 调用失败时直接报错并给出原因分类，不生成"假评估"。

### v1 范围
- 包含：自由输入、字段抽取与校验、智囊会诊（文字）、规则引擎（评级/双轴/档位/完整度/数据质量）、补全清单与重评、历史会话、lint、单元测试。
- 不包含：精评层（calc）、公网部署、登录、多用户、复盘回填、联网查询、语音输入、导出。

## 1. 硬约束

- 纯 Python 标准库（`http.server.ThreadingHTTPServer` + `sqlite3` + `urllib`），不得新增第三方依赖。
- **独立于 CCagent：** 所有代码与文件放在 `E:\Doc\Python_daye\CCagent\agent2\` 根目录；不得 import、引用或修改 CCagent 上级目录的任何文件；`agent2/career/` 和 `agent2/ev/` 只读，不得修改。
- 可以参考 CCagent 的 `server.py`（Host/Origin 校验、静态文件白名单、Gemini 调用与错误分类、重试策略）、`style.css`（Editorial 极简风），**复制后独立维护**。
- 本机运行：默认监听 `127.0.0.1:8100`，端口、Host 可由 `.env` 的 `PORT`、`HOST` 覆盖。
- `.env` 放在 `agent2/` 下，独立一份：`GEMINI_API_KEY`、`GEMINI_MODEL`（默认 `gemini-3.5-flash`）、`GEMINI_BASE_URL`、`GEMINI_TIMEOUT`（默认 120）。不得打印 Key。提供 `.env.example`。`.env` 不在静态白名单内。
- Windows 下 stdout/stderr 设为 UTF-8。
- **隐私：** 服务日志不得记录用户输入全文，只记录 session_id、版本号、输入长度、耗时、错误类别。

## 3. 数据模型（SQLite：`data/agent2.db`）

- `sessions(id TEXT PK, title TEXT, raw_text TEXT, created_at TEXT, updated_at TEXT, status TEXT DEFAULT 'active')`
  - `id` 形如 `s_YYYYMMDDHHMMSS_xxxxxx`；`title` 取 decision 或输入前 20 字。
- `evaluations(id TEXT PK, session_id TEXT, version INTEGER, fields_json TEXT, result_json TEXT, created_at TEXT)`
  - `result_json` 即第 8 节的结果对象。不保存 LLM 原始响应。
- 时间一律 UTC ISO 微秒 + `Z`，沿用 CCagent 约定。

### 字段状态（`fields_json` 中每个字段）
```
{ "id", "value", "unit", "category": "事实|自报|估计|猜测",
  "quote": "原话或空", "status": "given|ambiguous|missing|skipped",
  "readings": [], "source": "text|form", "ask_count": 0 }
```
- `status=missing`：未提及；`skipped`：用户点了"没概念/不想说"，视为已问满，不再询问，列入缺失项。
- 补全表单提交的字段：`source=form`，category 由用户选择：
  - "有账单/记录可查" → 事实
  - "我自己的实际情况" → 自报
  - "随便估的" → 猜测
  （对未来的计划类数字，最高只能是"估计"：如果用户选"有账单/记录可查"但字段属于未来量，如 first_paid_month、validation_months，则按"估计"处理。）

## 4. 字段注册表与适用性

注册表见 `prompts/fields_career.json`。`applicable_if` 取值语义（三值逻辑：未知视为可能适用）：

| 标签 | 适用条件 |
|---|---|
| `always` | 始终适用 |
| `cash_relevant` | `needs_cash` 不为 false **或** `affects_main_job` 不为 false（两者都明确为 false 即纯时间项目，不适用） |
| `outlay_relevant` | `needs_cash` 不为 false |
| `target_given` | `target_monthly_income` 已给出 |

## 5. LLM 调用（`llm.py`）

- 一次调用完成抽取 + 会诊文字。沿用 CCagent 的 Gemini `generateContent` + `response_schema` 结构化输出，temperature 0.2。
- Prompt 由 `prompts/career_council_prompt.md` 组装：
  - `{{FIELDS_INDEX}}`：每个字段一行 `id｜label｜type｜unit｜choices`。
  - `{{ADVISORS_INDEX}}`：每位智囊一行 `id｜name｜dimension｜common_pitfall｜advice_style`。
  - `{{LOCKED_FIELDS}}`：用户已通过补全锁定的字段（`id=value（category）`，每行一个）；首次评估为"（无）"。
- User 消息：用户原始文本（首次输入）；重评时在原始文本后附"以下为用户补充的内容"及补充条目。
- 响应 schema（Gemini 大写类型）：

```
{ decision: STRING,
  extracted: [ {id, value(STRING，数值/布尔统一转字符串，list 用 JSON 字符串), unit, category(enum 事实|自报|估计|猜测), quote, status(enum given|ambiguous), readings:[STRING]} ],
  advisors: [ {id, basis, missing:[STRING], note} ],
  critique: [ {target, text} ],
  two_week_checks: [ {side(enum supply|demand), text} ],
  validation_design: { supply:[STRING], demand:[STRING], threshold:[STRING] },
  clarify: [ {field_id, question, why} ] }
```

- 错误分类、重试策略沿用 CCagent：401/403→"Key 无效或无权限"，400→"请求被拒绝（可能是结构化输出参数）"，404→"模型名或 Base URL 不存在"，429→"限流"（重试 1 次，退避 2 秒），5xx→"服务繁忙"（重试 1 次），超时→"请求超时"（不重试），JSON 解析失败→"模型输出格式异常"。失败时 API 返回 `{error, category}`，前端明确展示原因，不生成评估。

## 6. 校验与 lint（`verify.py`）

### 6.1 抽取校验（对 `extracted` 逐项执行）
1. `id` 必须在字段注册表内，否则丢弃。
2. enum 字段 value 必须在 choices 内，bool 必须是 true/false，number 必须可转数值，否则丢弃。
3. **quote 必须是用户输入（含补充内容）的子串**（比较前统一空白、全半角标点）。不满足：丢弃该项并记录 `lint.dropped`。
4. number 类字段：value 中的数字必须能在 quote 中找到（阿拉伯数字，或常见中文数字"一到十、两、百、千、万"换算后相等）。不满足：丢弃该项。
5. category 不在四种内：按"自报"处理。对未来量字段（`first_paid_month`、`validation_months`、`weekly_hours_planned`、`target_monthly_income`）category 若为"事实"，降为"估计"。
6. 已锁定字段（`source=form`）永不被 LLM 抽取结果覆盖。
7. status=ambiguous 的字段，其 value 不进入规则引擎（按未提供处理），只作为补全/回译对象。

### 6.2 输出 lint（对 advisors.basis/note、critique.text、two_week_checks.text、validation_design.*、clarify.* 逐条执行）
1. **数字白名单**：文本中出现的阿拉伯数字（含中文数字换算）必须属于集合 = 用户输入文本中的数字 ∪ 已确认字段的数值 ∪ 规则白名单 {0、1、2、3、25、10、6、"两周"中的 2 等语境固定数字，由 `engine.py` 常量 `NUMBER_WHITELIST` 维护，初始包含 0,1,2,3,5,6,10,25,36}。不满足的条目：先让 LLM 重试一次（在 user 消息末尾追加"删除未出现在用户输入中的数字"），仍不满足则该条文字替换为"（该条含未核实数字，已隐藏）"，并在 `lint.hidden_count` 计数。
2. **违禁措辞**（命中即隐藏该条）：`停。`、`重复同一模式`、`又是试试看`、`你反复`、`别再用`、`废话`，以及正则 `你(这个人|总是|一直|习惯|性格)`。
3. **阈值标注**：`validation_design.threshold` 每条必须以"【用户确认】"或"【AI建议值】"结尾；缺失时由代码补"【AI建议值】"。含"【用户确认】"的条目，其主体文字必须是用户输入的子串，否则改为"【AI建议值】"。
4. `ai_impact` 相关文字必须含"判断，不是数据"，缺失由代码在末尾补"（判断，不是数据）"。
5. 数字白名单中的 36 等常量仅用于规则说明文字，LLM 不得主动使用评估期等概念。

## 7. 规则引擎（`engine.py`，纯函数，无 I/O，须有单元测试）

输入：字段状态 dict。仅使用 status=given 且 category 任意的字段值；ambiguous/missing/skipped 视为"未提供"。

### 7.1 各智囊评级（取值：高 / 中 / 低 / 无法判断 / 不适用）

**MONETIZATION**
- `paid_evidence=paid` → 高；`asked` → 中；
- `paid_evidence=none`：`precedent=yes` → 中；`precedent=no` → 低；`precedent` 未提供 → 无法判断；
- `paid_evidence` 未提供：`precedent=no` → 低；`precedent=yes` → 中；两者都未提供 → 无法判断。
- 规则说明里附上依据（读取了哪些字段）。

**EXECUTION**（三个信号各评一档，取最低；无信号 → 无法判断）
- 信号 A（需 actual 与 planned 且 planned>0）：比值 = `weekly_hours_actual_recent` ÷ `weekly_hours_planned`；比值<0.5 → 低；0.5≤比值<0.8 → 中；≥0.8 → 高。
- 信号 B（需 `continuity_weeks_12m`）：<16 → 低；16 到 30 → 中；≥31 → 高。
- 信号 C（需 `past_projects` 至少 1 项含 actual_months）：持续率 = （已完成或仍在做的项目数）÷ 项目总数。完成判定：`still_running=true`，或 `actual_months ≥ planned_months`（planned 缺失时只认 still_running）。持续率<0.5 → 低；0.5≤持续率<0.67 → 中；≥0.67 → 高。
- 以上阈值均为**经验阈值，仅供参考**，必须在 UI 的规则说明里标明。

**OPPORTUNITY**
- 优先使用 `floor_take_home_per_unit` 与"每单到手 = `unit_price` × `take_home_ratio`"比较：比值 x = 每单到手 ÷ 底线；x<0.8 → 低；0.8≤x<1.5 → 中；x≥1.5 → 高。
- 无到手底线、仅有 `floor_price_client` 与 `unit_price`：比值 = `unit_price` ÷ `floor_price_client`，同上阈值（说明里注明"这是客户付的价之间的比较"）。
- 缺少必要字段 → 无法判断。**不得混用两种口径。**

**SAFETY_NET**
- `needs_cash=false` 且 `affects_main_job=false` → 不适用。
- 生存月数 = `cash_free` ÷ `monthly_expense`（两者都有且 monthly_expense>0 才能算）。
- 花费占比 = `cash_outlay` ÷ `cash_free`（cash_free>0）。
- `borrowing_or_essential_funds=true` → 红线（见 7.3），评级为低。
- 生存月数<3 且 `needs_cash≠false`，或花费占比>0.25 → 低；
- 生存月数 3 到 6（不含 6），或花费占比 0.10 到 0.25 → 中；
- 生存月数≥6 且（花费占比<0.10 或 `needs_cash=false`）→ 高；
- 两类信息均不全 → 无法判断（只要其中一个可算且落在"低"，即评低）。

**STOPLOSS**
- 需要 `first_paid_month` 与 `validation_months`，缺一 → 无法判断。
- 时间条件：`validation_months ≥ first_paid_month + 2`。
- 时间条件满足且 `will_really_stop=true` → 高；时间条件满足且 `will_really_stop` 未提供 → 中；时间条件不满足，或 `will_really_stop=false` → 低。

**AI_IMPACT**、**CONSISTENCY**：不评级（`rating="不参与"`），只显示文字。

### 7.2 双轴合并
- 序数：低 < 中 < 高。
- **回报预期轴** = 合并 [MONETIZATION, EXECUTION, OPPORTUNITY]；**下行可承受性轴** = 合并 [SAFETY_NET, STOPLOSS]。
- 合并规则：取"不适用"之外的成员；已知评级 = 取值为低/中/高的成员；
  - 回报轴：已知评级不足 2 项 → 无法判断；否则取最低（木桶原则：成功需要"有人付费且你做得下来且划算"，是连乘关系）；
  - 下行轴：已知评级不足 1 项 → 无法判断；否则取最低；
  - 若有成员为"无法判断"，输出 `partial=true` 与 `unknown_count`，UI 显示"（另有 N 项未评，可能更低或更高）"。
- `purpose=learn` 时，回报轴固定输出"不适用（目的为学习：重点看下行轴与能否产出数据）"，行动档按下行轴判定。

### 7.3 行动档（取值：不建议 / 小额试验 / 可加大投入 / 暂不给档位）
按以下顺序判断，命中即停：
1. **不建议**（reasons 逐条列出，附算式）：
   - `borrowing_or_essential_funds=true`；
   - 生存月数<3 且 `needs_cash≠false`；
   - 花费占比>0.25。
2. **暂不给档位**：完整度<0.3，或两轴均为"无法判断"。
3. **可加大投入**：同时满足：回报轴=高、下行轴=高、两轴均无 partial、数据质量为 A 或 B、`paid_evidence=paid` 且其 category=事实。
4. 其他 → **小额试验**。数据质量为 C 时最高只能到"小额试验"。

### 7.4 完整度
- 对适用字段计算：分值 s = 1（given 且 category 为事实/自报/估计）；0.5（category=猜测，或 status=ambiguous）；0（missing/skipped）。权重 = 字段注册表 `weight`。
- 完整度 = Σ(权重×s) ÷ Σ(适用字段权重)，保留 2 位小数。
- 档位文案：<0.30 "初步印象"；0.30 到 0.59 "初步看法"；0.60 到 0.84 "较完整"；≥0.85 "完整"。

### 7.5 数据质量（A/B/C，仅当完整度≥0.3 时输出，否则输出"信息不足"）
- 关键参数共 5 项：`target_monthly_income`（收入目标）或 `baseline_monthly_income`（二者取已有的一项）、`paid_evidence`、`unit_price`、`weekly_hours_actual_recent`、`first_paid_month`。
- 每项"有证据"= given 且 category∈{事实, 估计}；"无证据"= 缺失、猜测、自报、ambiguous。
- 无证据≥3 项 → C；无证据 2 项 → B；其余 → A。（v1.0 规定 C 最高小额试验，已在 7.3 体现。）

### 7.6 补全清单（`to_complete`，最多 3 项）
- 候选：适用字段中 status 为 missing 或 ambiguous、且 `ask_count<2` 的字段。
- 排序：ambiguous 优先；其余按注册表 `priority` 升序。
- 取前 3 项，每项附 `ask_text`、输入控件类型（由 type 决定）、`choices`、`impact_note`、`reason`（missing/ambiguous）。
- `ask_count` 规则：每次提交补全（supplement）时，上一版 `to_complete` 中既未填写也未跳过的字段 `ask_count += 1`；被点"没概念/不想说"的字段设 `status=skipped`、`ask_count=2`。`ask_count≥2` 的字段不再出现在清单里，列入"缺失项"。**同一问题最多问 2 次，第 3 次不得再问。**
- 补全最多 6 轮（version 上限 7），超过后提示"信息已问满，请重新开始新评估或手动编辑"。

### 7.7 标志（`flags`，每项 `level: 红/黄` + `text`）
- 黄：`target_scope=project` 且没有个人层面数字（`target_monthly_income` 口径未确认）；
- 黄：计划小时 > 近期实际小时 × 2（计划与实际差距大）；
- 黄：给了 `unit_price` 但未提供 `take_home_ratio`（可能把客户付的价当成到手）；
- 黄：`stop_loss_rule` 原文为"反思/调整/再看看"之类，未给出可检查条件（用关键词 `反思`、`调整`、`再看看`、`看情况` 匹配）；
- 红：不建议的任一原因（借贷、生存月数、花费占比）；
- 红：`validation_months < first_paid_month + 2`（止损线早于首个付费月+2）。此时建议文字固定为："止损月不要早于预计首个付费月加2个月。可以延后止损月，或改用领先指标（如主动询问量、首个付费）作为止损依据；请不要把首个付费月估计改早。"

### 7.8 结论文案（代码模板生成，LLM 不参与）
- 前缀由完整度档位决定："初步印象："/"初步看法："/"较完整的评估："/"评估："。
- 模板（`{reward}`、`{downside}` 为评级文字）：
  - 暂不给档位："目前信息太少，还不足以给出行动建议。先补充下面几项，评估会更有依据。"
  - 不建议："综合来看，现阶段**不建议**投入。原因：{reasons}。"
  - 小额试验："综合来看，适合**小额试验**，先验证再决定是否加大。回报预期：{reward}；下行可承受性：{downside}。"
  - 可加大投入："综合来看，可以考虑**加大投入**。回报预期：{reward}；下行可承受性：{downside}。"
- 回报预期或下行可承受性为"无法判断"时，写"暂时无法判断"。
- 固定追加一行："这是基于你提供的信息的大致判断，不是精确数字。"

## 8. API

沿用 CCagent 的安全措施：Host 校验、Origin 校验、静态文件白名单 `{index.html, style.css, app.js}`、`/api/*` 同样校验。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/evaluate` | body `{text}` → 创建会话，调用 LLM，返回 result |
| POST | `/api/sessions/{id}/supplement` | body `{fields:[{id,value,category_choice}], skip:[field_id]}` → 合并锁定字段，重评，version+1，返回 result |
| GET | `/api/sessions` | 最近会话列表（id、title、updated_at、最新行动档、完整度） |
| GET | `/api/sessions/{id}` | 返回最新 result；`?version=n` 返回指定版本 |
| DELETE | `/api/sessions/{id}` | 硬删除会话及其全部版本（含敏感信息，必须真删除） |
| GET | `/api/advisors` | 智囊库 |
| GET | `/api/fields` | 字段注册表 |
| GET | `/api/config`、POST `/api/save-config`、POST `/api/test-connection` | 沿用 CCagent，仅 Key/模型/Base URL |

### result 对象
```
{ session_id, version, decision,
  completeness: {value, band},
  data_grade: "A|B|C|信息不足",
  axes: { reward: {rating, partial, unknown_count, applicable}, downside: {...} },
  tier: {value, reasons: []},
  headline,
  advisors: [ {id, name, rating, rule_note, basis, missing:[], note} ],
  fields: [ {id, label, value, unit, category, quote, status, source, ask_count} ],
  to_complete: [ {id, label, ask_text, type, choices, item_fields, impact_note, reason} ],
  missing_list: [ {id, label, why:"未提及|没概念/不想说|问满2次未答"} ],
  flags: [ {level, text} ],
  critique: [ {target, text} ],
  two_week_checks: [ {side, text} ],
  validation_design: {supply, demand, threshold},
  clarify: [ {field_id, question, why} ],
  lint: {dropped: [], hidden_count},
  disclaimer }
```
`rule_note`：规则引擎生成的评级依据（读取了哪些字段、按什么规则、代入的数值），例："单价 800 元 × 到手比例 0.6 = 每单到手 480 元；你的到手底线 600 元；比值 0.8，评为中（经验阈值）。"此处数字来自用户或规则常量，不受 lint 约束。

## 9. 前端（`index.html` / `app.js` / `style.css`）

沿用 CCagent 的 Editorial 极简风，页面尽量简单。评级不得仅用颜色区分（同时显示文字）。

### 页面结构（单页）
1. **输入区**：大文本框 + 一句提示"随便写，写不写数字都行：你想做什么？为什么？大概怎么赚钱？" + "开始评估"按钮 + 3 个示例点击填充（示例文字需泛化，不涉及真实个人信息）。
2. **结果区**（评估后显示）：
   - 结论卡：行动档、两轴徽标（回报预期 / 下行可承受性，含"另有 N 项未评"）、完整度条与档位文字、headline。
   - **补全区**（最显眼，紧接结论卡）：最多 3 张卡片，每张含 ask_text、输入控件（number / bool 开关 / enum 单选 / text / list 子表单）、来源三选一（"有账单/记录可查"、"我自己的实际情况"、"随便估的"；未来量字段隐藏第一项）、`impact_note`、"没概念/不想说"按钮。底部一个"补充后重新评估"按钮。ambiguous 项以回译方式展示：显示 `clarify.question`，并让用户选 readings 之一或手动输入。
   - 智囊会诊：7 张折叠卡，每张显示名称、评级、`basis`；展开显示 `rule_note`、`note`、缺失项。
   - 标志、批判、两周内验证 3 件事、验证设计、缺失项列表。
   - 版本对比：显示"上一版 → 本版"两轴与完整度的变化。
   - 固定免责声明："本评估基于你提供的信息做出的初步判断，不构成财务、法律或职业保证。AI 对具体职业的影响属判断，不是数据。"
3. **历史**：左侧或抽屉显示会话列表，支持打开和删除（二次确认，提示"删除后无法恢复"）。
4. **设置**：Key/模型/Base URL（沿用 CCagent 的设置弹窗）。

### 交互要点
- 评估中显示加载状态（预计 10–30 秒），失败时显示 `category` 与可操作提示，保留用户输入。
- 补全提交成功后，结果区原位刷新，并平滑滚动到结论卡。
- 不得在前端重新计算评级或档位，一律以服务端 result 为准。

## 10. 日志与错误
- 服务端日志格式：`[UTC时间] [级别] 事件 session=... version=... len=... ms=...`。不记录用户文本与 LLM 响应内容。
- 所有 `/api/*` 错误统一 `{ "error": "...", "category": "..." }`。

## 11. 测试与验收

### 单元测试（`python -m unittest discover tests`，不依赖网络）
`test_engine.py` 至少覆盖：
1. 每位智囊各评级分支（含边界：比值 0.5/0.8/1.5，生存月数 3/6，花费占比 0.10/0.25，验证期 = 首个付费月 + 2）。
2. 双轴合并：已知评级不足时输出"无法判断"；存在 partial 时标志正确；`purpose=learn` 回报轴为"不适用"。
3. 行动档：借贷 → 不建议；生存月数<3 → 不建议；完整度<0.3 → 暂不给档位；C 级不得给"可加大投入"；可加大投入的全部条件。
4. 完整度与数据质量的计算（含纯时间项目的适用性）。
5. 补全清单：ambiguous 优先；`ask_count≥2` 不再出现；skip 后进入缺失项；最多 3 项。
6. 标志：止损线早于首个付费月 + 2 时为红。

`test_verify.py` 至少覆盖：
1. quote 不是原文子串 → 丢弃；数字不在 quote 中 → 丢弃；中文数字换算（"三个月" = 3，"两万" = 20000）。
2. lint：新数字被隐藏；违禁措辞被隐藏；threshold 标注补全；"【用户确认】"但不是用户原话 → 改为"【AI建议值】"。
3. 锁定字段不被 LLM 覆盖。

### 验收用例（`tests/golden/cases.json`，AGENT 按下列意图编写 ≥8 条输入，需联网时手动跑，结果记录在 `tests/golden/RESULTS.md`）
1. 只有一句"想做自媒体"：期望回报轴=无法判断，档位=暂不给档位，完整度<0.3，补全清单 3 项。
2. 明确说"打算借钱做"：期望档位=不建议。
3. 含"51 小时也能接受"：期望对应字段 status=ambiguous，clarify 非空，且该值不进入评级。
4. 用户说"画室每月净利 2 万"：期望出现 `target_scope` 补全或黄色标志，不得把 2 万当个人到手。
5. 用户把咨询定价说成"最低接受时薪"：期望不把它填进到手底线（status=ambiguous 或不抽取）。
6. 止损"做 2 个月没结果就停"且首个付费月为第 3 个月：期望红色标志。
7. 纯时间项目（不花钱、不影响主业）：期望 SAFETY_NET=不适用，补全清单不含 cash_free。
8. 目的为学习：回报轴=不适用。
9. 同一输入重复评估 3 次：两轴评级与档位应一致（评级由规则引擎产生，抽取字段允许轻微差异，但 category 与 status 不得互相矛盾）。
